# 宝塔批量上传文件与目录

状态：待用户确认功能范围；尚未编写实现或部署。

## 用户需求

在现有宝塔批量管理平台中，一次选择多台面板或分组，上传本机文件或目录。用户已明确选择：覆盖已有同名文件，执行前确认。目标绝对目录既可统一设置，也可逐台单独设置，单独设置的优先级高于统一设置。

## 推荐方案与替代方案

推荐使用已保存的宝塔 API 配置：本机文件先传到 Spug 私有暂存区，同一份文件复用于各面板，通过官方文件接口下发。这样可以直接使用现有面板分组、权限、预检和执行记录。

另有两种方式：经 SSH/SFTP 分发，适合已有主机 SSH 凭据的场景，但会额外要求每台主机授权；由目标下载外部 URL，适合大型公开包，但需要可访问的下载源。此次选择 API 上传，不要求新增 SSH 凭据或公开下载链接。

## 用户流程

1. “批量执行 → 面板任务”新增“上传文件 / 目录”。
2. 选择面板或分组，选择多个本机文件或一个目录。
3. 设置“统一目标目录”，也可填写各面板的“单独目标目录”。每台优先使用其单独目录；单独目录留空则沿用统一目录。选择目录时保留所选目录自身名称及内部层级，例如 `dist/css/app.css` 上传至 `/www/wwwroot/demo/dist/css/app.css`；选择多个普通文件则直接放入最终目标目录。
4. 文件先暂存到 Spug，显示文件数量、总大小及暂存进度。关闭页面后，已确认的远端任务由后台继续执行。
5. 生成预检，逐台显示目标目录、文件数、预计新增/覆盖数、目录/文件同名冲突或权限错误。预检不调用上传、建目录或覆盖接口。
6. 开始前必须勾选“确认覆盖目标目录内的同名文件”。确认基于本次冻结的面板、文件清单和路径；变更选择或路径需要重新预检。
7. 执行页默认仅显示各面板进度和成功/失败/待核实数量。失败文件及完整清单按需展开，遵循刚完成的简洁结果布局。

## 目录和覆盖语义

- 目标目录优先级固定为：非空的单独目录 > 统一目录。空白输入按留空处理；两者都未填写时阻止该次预检，并提示具体面板缺少目标目录。统一目录可以留空，但所有选中面板此时都必须填写有效的单独目录。
- 两种目录均须通过绝对路径校验。已填写但无效的单独目录直接提示错误，不静默退回统一目录。修改统一目录只影响沿用统一目录的面板，不覆盖已填写的单独目录；清空某台单独目录则恢复沿用统一目录。
- 表单和预检逐台展示“最终目标目录”及来源（单独设置／统一设置）。创建预检时服务端固化每台最终路径；随后表单修改不改变已生成任务的冻结路径，必须重新预检。
- 保留相对目录层级，自动创建上传文件需要的父目录。浏览器目录选择不能可靠枚举空目录，首版明确不承诺保留空目录。
- 覆盖仅针对本次清单中完全相同路径的文件；目标的其他文件保持原样，不做目录镜像删除，也不自动解压用户选中的压缩包。
- 文件与目录同名属于冲突，预检阻止该项目，不先删除目录或文件为上传让路。
- 上传前重新检查冻结范围与路径；发现目标类型变化、API 配置变化或源文件摘要变化时阻止该项。最终预检仍不能保证远端没有并发修改，界面不承诺跨服务器原子提交或自动回滚。

## 接口依据及实现边界

已核对本任务保存的官方文档 `https://docs.bt.cn/api/files/actions/index.md`，以及宝塔 Linux 9.2.0、11.7.0、13.1.0 的 `files.py` 对应源码：

- `POST /files`，`action=UploadFile`，multipart 字段为 `path`、`zunfile`、`request_time`、`request_token`。签名放请求体；文件名只传最终 basename，相对目录由已验证的目标路径构造。
- `UploadFile` 会创建不存在的目标目录，并直接保存/覆盖文件；成功响应并不构成内容校验，更不代表网站运行成功。采用逐文件持久记录，避免将整个目录用一个成功提示概括。
- `upload_files_exists` 的实际返回为每条路径包含 `filename/exists/size/mtime/isfile` 的列表，文档的简单“已存在路径列表”描述不足，按适配源码和夹具解析。
- 不使用 `GetFileBody` 核验任意文件；已知其存在特定路径下创建文件的副作用。真实内容核验使用经审查的流式只读下载并计算摘要；无法取得可靠读回时标为待核实，不仅凭文件大小认定内容一致。
- 三个版本的协议核对是源码依据，尚不等于真实上传实测。验证使用隔离夹具，不向客户网站投放开发测试文件。

## 存储、调度和限制

源文件以随机内部标识保存在数据卷私有目录，记录所属用户、原相对路径、大小和 SHA-256；不进入静态网站目录、Git 或任务 JSON。接口校验所属用户与任务权限，文件内容不回显到日志、审计或错误消息。

上传采用磁盘暂存和流式转发，并发面板数沿用现有上限 2。首版默认单文件最多 20 MiB、每批总计 200 MiB、每批最多 1000 个文件、最多 50 个面板；限制由服务端配置并返回界面。全局暂存上限 1 GiB，每用户上限 400 MiB，暂存时至少保留 512 MiB 磁盘余量。容量不足或超限在开始远端任务前拒绝，不能静默漏文件。文件级记录单独分页存储，任务详情只保存与返回汇总，不把全部文件清单塞入现有任务 JSON。

任务持久化每个文件的派发意图和结果，同一面板串行执行；取消只停止未下发文件。超时或进程中断的项目保留待核实，不盲目重新覆盖。重新预检重试需再次确认覆盖。

未绑定任务的暂存草稿 24 小时过期，已结束任务的源内容保留 7 天。暂存清理不影响运行、待核实或未过期预检的任务。内容清理后，历史结果和文件摘要保留；重试时如源已过期，要求重新选择文件。

## 验收标准

- 一次上传多个普通文件或有嵌套目录的文件集合到多台面板，路径映射明确。
- 公共目录为 `/www/wwwroot/common`、面板 A 单独目录为 `/www/wwwroot/site-a`、面板 B 单独目录留空时，A 使用单独目录，B 使用公共目录；更改公共目录不会改变 A，清空 A 的单独目录后 A 恢复使用公共目录。无最终目录或单独目录无效时不能生成预检。
- 预检显示覆盖范围，未确认覆盖不可执行；仅选文件受到影响。
- 文件与目录同名、相对路径穿越、重复目标、大小/数量超限、跨用户暂存引用和 API 配置变化有明确错误。
- 断连、进程恢复、取消和重试不会无记录重复派发；响应成功但内容不符不会标成功。
- 验证现有面板任务不回归，前端保持简洁。部署前保留现有数据、密钥、任务历史并核对健康状态。
