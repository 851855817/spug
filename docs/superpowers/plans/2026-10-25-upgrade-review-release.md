# 升级核对增量发布计划

夜间计划第 3 项的实施规格。用户已授权部署；沿用现有草稿 PR #4，不合并。新功能已在应用提交 `0238dca` 完成，后续发布工具提交不改变其业务范围。

## 固定范围

相对上一应用版本 `5e6f50da476ea993273981366ed160e4cfb675bd`，只覆盖运行时 `apps/baota/operations/php_update.py` 和已构建前端。源码导出包含隔离测试所需文件；实际覆盖清单只有该运行时文件。拒绝夹带其他 API、模型、settings 或 scheduler 改动。本次不运行 makemigrations／migrate，不清空库存或到期记录。

新镜像基于实际旧版本 `spug-baota:5e6f50d`，继承既有九服务接线和迁移历史；仅供未来重建。现有演示容器保持原 ID，不为了发布重建容器。Redis、原 worker、monitor 保持原 PID。

## 实施顺序

1. `deploy/upgrade-review/package.py PREVIOUS --node NODE` 仅接受清洁工作树，检查运行时变更范围，重新生产构建，核对构建期间 HEAD 和工作树未变。导出跟踪源码并统一 LF，生成 API／UI／辅助脚本摘要以及旧运行时预期摘要。打包到工作树以外的 `upgrade-REV7.tar.gz`，记录完整归档摘要。
2. `prepare.py REVISION ARCHIVE_SHA256` 校验归档、路径／链接／大小边界和旧镜像标签后构建镜像。以不可变镜像 ID 运行实际镜像内的 API／UI 摘要核对、完整隔离后端回归及镜像接线；在隔离文件系统执行发布失败测试。所有阶段禁止写入源码字节码，结束时再次核对镜像标签与 ID，并把 ID 写入准备回执。准备阶段不挂载生产数据、不执行客户操作。
3. `fingerprint.py --require-idle` 只查 Spug 数据库、Redis、本地套接字与进程。覆盖全部已安装业务模型及自动关系表，包含非空库存、全部到期表、用户／角色／主机扩展、凭据、配置、通知和部署；只有宝塔监控采集缓存两表的行数据除外。数据库实际全部表（含缓存、迁移和未建模表）的列及约束独立形成完整模式摘要。输出行数／摘要、模式和迁移记录摘要、密钥摘要及可解密标记，不输出记录或凭据。
4. `publish.py REVISION PREVIOUS` 使用非阻塞独占进程锁，必须匹配实际线上 UI、两份运行时原文件摘要、原 Compose 语法及镜像行、隔离验证回执、实际镜像 ID 和辅助脚本摘要。发布前逐文件将暂存目录与受校验归档绑定，只有准备回执可不在归档中；复制到容器后再次独立核对将执行的脚本、API 与所有静态资源。先确认资源、九服务和业务空闲，再停止健康自动恢复及六项必要写入入口。停止后再验证一次空闲和原业务摘要。源码摘要只排除 API 根目录的动态日志与 Python 字节码，其余配置、业务数据和嵌套目录仍须一致。新 UI 辅助脚本固定备份／恢复 `index.html`、`asset-manifest.json`、`ui-release.json`、`service-worker.js` 四个入口；其他已有同名静态文件若字节不同，必须在停止服务前拒绝发布。
5. 完成数据库与全数据卷配对备份，校验压缩结构／归档及 SHA-256，保存原 Compose 与健康配置，备份权限为 0700／0600。复用已测的受保护 API／静态覆盖辅助脚本，尝试标记必须在调用之前记录。
6. 开放入口前验证业务、密钥、模式和迁移记录保持一致；核对两份运行时文件及 UI 资源摘要。更新未来重建镜像；恢复六服务后确认九服务 RUNNING、HTTP 200、UI revision、新源文件与原容器／旧 PID 一致，再恢复健康 timer。

保全比较的两个动态字段边界：认证中间件每次已登录 GET 都延长 `User.token_expired`。只对启用用户且已有 32 字符令牌的有效未来整数 TTL 归一为有效标记；令牌本身、密码、权限、用户数量以及撤销值 0／已经过期的值仍原样参与摘要，禁用用户或无效令牌的 TTL 也保持完整比较，数据库不作修改。源码比较另排除 API 根目录的精确 `supervisord.log`，因为停止服务本身会追加该日志；同名嵌套文件、UI 文件和未知轮转文件仍须参与摘要。完整数据卷备份仍包含这些原始值／日志。

## 失败处理

首个 `d1be858` 产物已通过 Linux 隔离验证及 GitHub CI。真实发布预检发现 CRA 生成的 `service-worker.js` 会改变、旧三入口辅助脚本无法保全，因此按规则在停止服务前拒绝。线上保持 `5e6f50d`，没有覆盖、停服或修改数据库。后续产物将使用独立四入口辅助脚本，须重新提交、打包、验证，不在服务器手改受校验产物。

`37fd259` 的新产物也通过完整隔离检查和 CI；维护入口关闭后比较因会话 TTL 和 supervisor 日志变动拒绝，尚未备份／覆盖应用。根据保存的完整前态，只读验证原 API／UI／Compose 未变化、原容器与三进程未变化、模式／密钥和其余业务行相同，随后直接恢复原 `5e6f50d` 九服务及健康 timer，没有降级任何新代码或回写用户数据。后续必须从新的清洁提交重新准备，不复用该回执。

备份未完成时不允许覆盖。辅助脚本部分失败后不能假定其内部恢复成功，必须显式恢复并校验完整原始收据与实际文件。任何模式漂移、原数据漂移、恢复缺口或未知状态均不得重新开放入口或健康自动恢复。

若新入口可能已经开放，回退前先再次停止六服务、确认空闲和原业务摘要；存在新 `health_policy` 的在途任务时禁止旧 worker 接管。不能用旧模块验证合同将新任务误判成功。旧在途任务也不能因部署自动重发。

恢复仅针对源码／静态与配置，不做数据库逆向迁移或自动覆盖整库。配对备份验证不等于完成生产整库恢复演练。
