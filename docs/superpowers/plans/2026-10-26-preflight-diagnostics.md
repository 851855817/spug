# 发布预检诊断实现计划

> 依据已授权夜间计划执行现有发布问题的诊断改进，沿用 executing-plans。起点 `fd9f1de`；不重新发布应用，不在客户运行操作。

**目标：** 为上轮只返回 `failure=preflight` 的拒绝补充固定检查项，后续能判断应核查版本、配置、服务、空闲、进程还是文件。

**架构：** 保留原 `failure` 和恢复合同，仅在预检失败响应增加 `preflight_check`。控制器按原调用顺序维护内部固定检查名称，不序列化任何异常、命令、地址、路径或客户数据。成功、归档拒绝、维护后的失败没有这个附加字段。

**技术栈：** Python unittest，已有 FakeHost 状态夹具；不依赖 Docker、客户接口或数据库。

## 规格与取舍

- 使用附加检查字段，兼容现有按 `failure=preflight` 判断的调用方；直接拆换 `failure` 名称会改变原合同，因此不采用。
- 检查名称固定为 `revision`、`compose`、`services`、`business-idle`、`process-identity`、`runtime-files`、`runtime-baseline`。读取失败与已取得证据不符合合同都指向对应项，检查名称不从异常推导。
- `compose` 包含读取、目标文本构造及原配置校验；`business-idle` 包含完整业务／模式／密钥摘要和空闲核对；`runtime-files` 是读取完整快照，`runtime-baseline` 是与基准／允许静态覆盖合同核对。
- 调用顺序、所有门、备份、维护、发布和恢复保持原逻辑；新增字段不表示允许重试或跳过检查。首次生产拒绝的原因仍未知，离线复现的是诊断缺少分项信息，不宣称定位了首次原因。
- README 提供分项排障映射，要求重新完整只读核查，任何不满足时保留正常服务。
