# 宝塔论坛需求调研与 Spug 功能建议

调研日期：2026 年 10 月 23 日。对照平台：本项目当前二开版本，源码基线 `686811b`，现有功能见 [平台使用手册](../spug-platform-user-manual.md)。

## 1. 先看结论

**有值得继续做的功能。最适合你的方向是：让 Spug 汇总多台宝塔的业务状态，发现需要处理的事项，再调用已经有的批量任务去处理。**

建议第一批优先做 **证书与网站资产总览、备份结果核验、升级前后健康检查**，同时补一个投入相对小的 **服务器到期提醒**。资源监控历史和阈值告警可排在下一批；如果准备让客户或外包人员直接登录，客户数据权限应提前完成。

论坛中已经有人要求批量上传目录、批量伪静态、命令分类和自动 Git 部署。你的平台已经覆盖其中不少能力，后续应完善使用体验和核验能力，避免反复开发同一功能。

本文的优先级是根据“多客户、多服务器、宝塔 Linux、减少逐台操作”的使用情境给出的产品判断，不是论坛投票结果，也不是已通过验证的开发工期。

## 4. 第一批功能应该怎样做

### 4.1 网站与证书统一资产页

**真实需求：**有人反馈证书超过 100 条会卡死；有人希望部署页面显示剩余有效期和当前网站名；有人指出宝塔页面看似正常，但证书链实际有问题。[证书列表卡顿](https://www.bt.cn/bbs/thread-155880-1-1.html)、[部署页剩余时间](https://www.bt.cn/bbs/thread-152095-1-1.html)、[证书链核验](https://www.bt.cn/bbs/thread-110958-1-1.html)。

建议放在“宝塔面板管理 → 网站/证书资产”，支持按客户、分组、服务器、域名和到期状态筛选。首版列出客户、服务器、站点、域名、证书类型、到期日、最近成功采集时间和采集错误；使用服务端分页，避免一次加载所有证书。

第一步以只读总览和到期提醒为主，第二步从异常行跳转到已有 SSL 面板任务，第三步再加 DNS 验证、通配符和自动部署。记录必须区分“未配置”“采集失败”“未知”，采集失败不能显示为正常。暂停/删除站点及非 ACME 证书应有明确的续签策略。

**使用例子：**客户甲有 6 台宝塔、80 个站点，按“14 天内到期”筛出 9 个域名，先核对实际对外证书，再选适合 HTTP 验证的项目创建已有续签任务，其余进入 DNS 验证待办。

证书需要区分源站和 CDN：直接访问公网域名可能读到 CDN 证书，不能据此证明源站已经更换；同样，面板保存了新证书也不证明 Web 服务已加载。核验应保留目标、SNI、证书指纹和时间。

**复用现成项目：**论坛已有 [ALLinSSL 使用介绍](https://www.bt.cn/bbs/thread-146153-1-1.html)，本轮也核对了 [项目仓库](https://github.com/allinssl/allinssl) 当时默认分支 `1.1.4` 的 README 与仓库元数据，其声明覆盖证书申请、续签、多平台部署和到期监控，许可证标注 AGPL-3.0。可先比较“Spug 做资产与任务入口，复用外部证书引擎”和“继续扩展现有模块”的成本。本轮没有审计其代码或验证集成 API，不能直接认定接上即可使用。

### 4.2 备份状态与恢复核验

**真实需求：**只备份重要表、排除不需要的网站或大目录、备份网站配置，以及灾备数据真正恢复不出来。[多表策略](https://www.bt.cn/bbs/thread-142133-1-1.html)、[按站点排除](https://www.bt.cn/bbs/thread-112288-1-1.html)、[配置一起备份](https://www.bt.cn/bbs/thread-52505-1-1.html)、[异地恢复失败](https://www.bt.cn/bbs/thread-64468-1-1.html)。

先做“备份检查台”，汇总现有备份任务结果，显示预期周期、最近成功时间、文件大小、存放位置、保留天数、核验结果和负责人。要明确区分四层状态：任务说完成、备份文件实际存在、文件可读取/归档可打开、在隔离环境中恢复成功。

**使用例子：**20 台服务器每天有备份任务，但其中一台因磁盘不足连续失败。Spug 显示“客户乙 / 数据库 / 48 小时无有效备份”，通知对应负责人；排查后在测试环境做一次恢复抽检，保存结果。

之后再做统一备份计划、排除规则、对象存储和恢复编排。恢复需要核对数据库版本、业务写入及配置差异，不宜把“下载成功”称为“可以恢复”。网站文件、数据库和配置的时间一致性也需要单独处理。

旧帖还反映了云端备份密钥和删除权限的担忧。[原帖](https://www.bt.cn/bbs/thread-98672-1-1.html)。这里的产品启示是让备份具备独立保留策略和受限删除权限；只把密钥加密保存，不能保证服务器失陷时备份依然安全。

### 4.3 升级影响清单与健康检查

**真实需求：**安装/更新 PHP 改变 CLI 版本导致定时任务出错；更新后 Redis 扩展装不上；商店没有预期更新按钮。另有旧帖中官方明确担心“一键更新”造成服务启动失败。[CLI 版本变化](https://www.bt.cn/bbs/thread-62811-1-1.html)、[扩展问题](https://www.bt.cn/bbs/thread-156203-1-1.html)、[更新按钮](https://www.bt.cn/bbs/thread-156228-1-1.html)、[一键更新答复](https://www.bt.cn/bbs/thread-54171-1-1.html)。

你已经有 PHP 同分支更新和面板升级，因此建议补充升级前后的环境比较：实际版本、使用它的网站、CLI 默认版本、关键扩展、FPM 进程/监听、指定健康检查网址，以及升级后的变化。执行继续复用当前预检、逐台结果、并发限制和待核实处理。

**使用例子：**要更新 15 台服务器的 PHP 7.4，先确定每台当前状态和影响站点；仅对一台测试目标执行，核对 FPM、扩展和指定页面，再处理后续批次。某台更新了 CLI 但 FPM 异常，必须显示部分完成或待核实，不能整批标绿。

论坛里的漏洞名称、版本号和补丁说法只当需求线索，不能直接变成安全判定依据。版本与补丁目录应来自经核对的官方通告和实际软件信息；本轮没有验证帖子所述漏洞的真实性或影响范围。

### 4.4 服务器到期提醒

**真实需求：**用户多云、多台服务器，忘记续费；希望资产按到期时间排序，到期前变黄和通知。[2026 年多机提醒建议](https://www.bt.cn/bbs/thread-155287-1-1.html)、[资产提醒与排序](https://www.bt.cn/bbs/thread-74347-1-1.html)、[多云忘记续费](https://www.bt.cn/bbs/thread-33143-1-1.html)。

复用 SSH 主机已有到期字段，增加负责人、提醒时间、处理状态；同机关联的宝塔记录共享资产归属。建议每日运行，支持 30/7/1 天提示和“已续费，更新日期”。面板独立纳管的记录允许手填日期，并明确来源是人工还是云 API。

**使用例子：**同一客户在不同云厂商买了 8 台机器，进入“未来 30 天到期”，看到其中 2 台及其负责人，通知后更新续费日期。域名和服务合同可以后续纳入，但不能承诺所有域名到期时间都能自动准确查询。

### 4.5 后台资源历史与告警

**真实需求：**磁盘使用率达到自定义阈值通知、带宽过高报警、历史图表按更粗粒度展示。[磁盘阈值](https://www.bt.cn/bbs/thread-69590-1-1.html)、[带宽告警](https://www.bt.cn/bbs/thread-146324-1-1.html)、[图表粒度](https://www.bt.cn/bbs/thread-94653-1-1.html)。

当前资源卡片需要页面在场，原生监控任务虽可后台执行，但并没有直接提供这套资源数据的历史与阈值规则。可在现有监控中心扩展后台采集、趋势和规则，复用原生通知通道。

仍保留“默认关闭，开启才采集”的约定。后台采集应单独明确启用；建议先以 5 分钟轻量采集、2 个并发、失败退避和有限保存周期起步，再根据实测调整。100 台机器每 5 分钟一轮，平均约 0.33 次采集/秒；这只是请求量计算，不是负载保证。目录扫描、日志和完整进程列表不应每轮采集。

**使用例子：**夜间磁盘连续 3 次超过设定阈值，通知里带“客户丙 / 订单服务器 / IP / 挂载点”；进入后能看最近 24 小时曲线，空间恢复后关闭事件。采集失败和数据过期需要另行展示。维护窗口、告警合并、恢复通知与通知静默应分开处理，避免将“故障状态”隐藏。

### 4.6 客户/站点权限与审计

**真实需求：**外包长期维护只允许接触一个网站，不想共享主账户；临时授权时间短，也无法满足指定目录/站点权限。[单站点隔离](https://www.bt.cn/bbs/thread-154246-1-1.html)、[外包子管理员](https://www.bt.cn/bbs/thread-135467-1-1.html)、[子账号需求](https://www.bt.cn/bbs/thread-142912-1-1.html)。

建议沿用现有账户角色，为客户分组、面板和站点增加服务端数据授权；查询、执行、日志、导出、文件入口和缓存都按同一范围检查。审计统一记录操作者、客户、目标、动作、前后摘要、执行结果和关联任务。

**使用例子：**给外包人员分配“客户丁 → 展示站 → 上传和指定发布操作”，他看不到其他客户的面板、凭据和任务。不能把 SSH 终端或任意 Shell 模板同时开放，再声称其只能访问一个站点。

宝塔 API 密钥本身仍可能拥有较大权限，Spug 只能约束经 Spug 发起的操作；它不会自动改变客户宝塔主账户的权限，也不能限制别人绕过平台直接操作服务器。[API 权限与白名单答复](https://www.bt.cn/bbs/thread-74066-1-1.html)。

## 5. 第二批功能的具体边界

| 功能 | 可以先交付什么 | 原帖与需要注意的边界 |

## 7. 暂不建议优先做什么

**同版本 PHP 多 FPM 池。** [原帖](https://www.bt.cn/bbs/thread-155847-1-1.html)希望不同站点使用同版本下不同池，场景成立；但不能直接采信“性能大增”的判断。实际涉及 Web 配置、进程限额、扩展和宝塔管理状态的一致性，应先明确隔离需求并做压力测试，更适合在宝塔本身适配后由 Spug 编排。

**重新做一个完整 WAF、数据库管理器或 Docker 应用商店。** 跨服务器的策略汇总、配置检查和任务入口适合 Spug；在平台里重做底层防护、全部数据库引擎或全部容器生命周期，维护面会迅速扩大。

**无条件一键更新/修复全部服务器。** 论坛更新失败和兼容问题能说明需要影响评估与核验，不能证明某个通用脚本可以解决。网络超时、面板报错、缓存旧版本和目标软件不兼容也应分开诊断。

**把所有论坛脚本或非稳定接口直接开放为任意 API 执行。** 有用户找上传、Shell 和项目 API，但官方回复并不构成稳定接口承诺。[上传 API 求助](https://www.bt.cn/bbs/thread-129713-1-1.html)、[Shell API 求助](https://www.bt.cn/bbs/thread-141746-1-1.html)。继续采用按版本验证的适配器，确认输入、返回、幂等性和读回依据后再开放。

有些帖子已指向插件或现有能力，例如 [SSL 到期通知旧帖](https://www.bt.cn/bbs/thread-77611-1-1.html)中的官方回复提到异常监控插件。它仍能证明用户场景存在，但不能用它声称“宝塔至今完全没有证书提醒”。

## 8. 推荐实施顺序

1. **先整合数据：**网站/证书资产、现有备份检查、服务器到期提醒。把多机查询、缓存、最近成功时间、错误状态和分页做好；先让你每天知道哪里需要处理。
2. **再完善处理结果：**升级前后检查、有限文件副本、资源后台历史和告警。继续沿用已有任务记录、并发限制、冻结预检和待核实处理。
3. **最后增加自动化：**DNS 证书、跨平台部署、备份恢复流程、面板任务计划/流水线、环境方案。只有受支持的版本和操作才进入自动执行。

如果要开放给客户或外包使用，客户数据授权和审计需在第 1 阶段前或同时完成；只有你本人维护的情况下，可按实际使用安排。

这能形成清晰的日常工作流程：**全局看异常 → 按客户/服务器定位 → 生成适配的任务 → 检查实际结果 → 留下可查询记录。** 本轮产出是调研和候选范围，没有开始实现上述新增功能。
