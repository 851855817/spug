# 升级信息查询故障处理

## 现场证据

两台已保存的宝塔 Linux 9.2.0 均能通过签名 API `/system?action=GetSystemTotal` 返回实际版本；无 `force` 的 `/system?action=upgrade_panel` 返回 404。只读核对客户实际安装源码，升级方法及路由存在。对其中一台正常登录后查询同一接口，得到 HTTP 500、`JSONDecodeError`，确认不能把 API 会话下被隐藏的 404 解释为接口不存在或地址缺少安全入口。

客户实际源码从官方 `get_panel_version` 端点读取内容并直接解析 JSON。两个客户配置的官网节点均为 `www-node3.bt.cn`。从管理服务器和开发机访问该官方公开端点，得到 HTML 错误页或超时；官方 node.json 中的其他 www 节点同样未取得有效候选。更换 User-Agent 也没有恢复查询。没有找到验证可用的官方替代入口，没有修改客户节点配置。

这些证据能确认一次客户升级查询内部 JSON 解析异常，以及当前公开端点在两个诊断环境不可用；不能据此断言第二台内部异常完全相同，或排除所有客户网络问题。没有对客户执行升级、安装软件、运行修复脚本。

## 平台修复

- 系统身份查询仍严格校验；身份查询失败不降级成升级目录失败。
- 身份已核实但升级查询失败时，返回实际版本、适用升级模式、`upgrade_available=false`、空候选和固定提示。不会把远端正文、凭据或栈信息传给浏览器。
- 9.2 保留官方稳定通道界面，读取失败或读取中禁选；提供“重新读取升级信息”。新请求开始立即使父表单的旧候选失效，旧请求结果不覆盖新请求。
- 无效现代官方元数据不再被当作“当前没有更高版本”；合法官方版本等于当前版本仍可得到有效空升级列表。
- 表单在读取中或失败后阻止沿用旧值创建预检。服务端预检及执行前仍重新查询真实候选；没有缓存候选、伪造版本或使用旧 `UpdatePanel` 回退。

## 验证及限制

回归覆盖 9.2 查询故障与重新读取恢复、现代字段缺失与合法最新版、身份失败、前端重读失效及失败后的提交阻断。独立审查发现现代空云端字段被误判为成功，增加失败测试后修复。

平台错误处理修复不等于官方升级服务恢复。只有客户面板实际返回有效升级候选并通过预检，才能声称其升级查询恢复；本记录不声称客户升级执行已经验证。
