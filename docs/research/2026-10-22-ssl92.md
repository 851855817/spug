# 宝塔 9.2 SSL 主配置证据适配

日期：2026-10-22。依据本地官方 9.2.0 源码与独立协议夹具完成申请、续签和独立部署阶段适配。本次没有执行宝塔源码、连接客户面板、请求真实 CA 或操作客户网站。真实线上 TLS、include 内容和面板同步结果仍未验证。

## 官方来源与根因

来源沿用 [9.2 审计](2026-10-22-baota-9.2-audit.md)：官方 `LinuxPanel-9.2.0.zip`，SHA-256 `44ccad5f7dbbcb5f2bb502bf2d9fba8496a18ca82c873dec1ba043967ff40aae`。下列源文件位于 sibling `../baota-api-research/source-reference/9.2.0/`，只读、未执行。

- `panel__class__panelSite.py:2653-2663`：`GetSSL` 只读 canonical `/www/server/panel/vhost/cert/<site>/fullchain.pem`，公私钥都不存在时才退到 `/etc/letsencrypt/live/<site>`；`:2686-2699` 仅用 `conf.find` 判断启用状态。因此 canonical 新证书加 `status=true` 不能证明实际配置使用它。
- 同文件 `:2117-2131` 的 Nginx 默认 SSL 指令与 `:2266-2290` 的 Apache SSL VirtualHost 均引用 canonical 公私钥路径。`:272-329` 的 Nginx 站点模板包含 well-known、extension glob、enable-php、rewrite include；`:161-185` 的 Apache HTTP 模板包含 extension glob。
- `panel__BTPanel____init__.py:1428-1480`：`/download` 通过 `comm.local()` 鉴权、对缺失文件/目录直接拒绝；不会创建目标目录或文件，成功为 octet-stream attachment。`:1471` 的下载审计日志仍可写入。
- `panel__class__acme_v2.py:1134-1207,1289-1340`：签发保存和 `sub_all_cert` 可能自动同步面板范围内同 SAN、issuer 和有效期符合条件的证书，并重载 Web。`:2288-2296` 续签可能裁剪订单 SAN。
- 对照 13.1.0 `panel__class__panelSite.py:2628-2644` 才解析实际证书指令路径。本次主配置适配仅用于 9.2.0，不改变现代版本原有证据路径。

## 受限读取与判定

新增内部方法 `PanelClient.read_site_web_config(server, site_name)` 仅接受 Nginx/Apache 和服务器已核实的网站标识，构造 `/www/server/panel/vhost/<server>/<site>.conf`，上限 256 KiB。`read_site_public_certificate(site_name)` 仅构造 `/www/server/panel/vhost/cert/<site>/fullchain.pem`，上限 128 KiB。两者复用已有固定 `/download`、GET body 签名、流式大小/总时限、重定向拒绝与 TLS CA/pin。浏览器不能提交路径；没有通用文件读取、目录遍历、shell、私钥下载或项目名前缀回退。

9.2 的选定 PHP/静态站点快照先解析主文件，再读取 `GetSSL` 和固定公开证书，要求公开证书元数据及 SHA-256 指纹一致；最后重读主文件以发现读证书期间的配置变化。实际证书/私钥指令只允许本站 canonical 路径。读取私钥路径字符串只用于验证配置，没有下载对应文件。

Nginx 只接受一个完整顶层 `server`，分辨引号、注释与作用域，要求证书、key、SSL listen 和网站名在同一直接作用域，拒绝额外 server、重复证书、多路径、变量路径、未知证书提供器和不完整语法。Apache 支持标准 HTTP 加单个 TLS VirtualHost，要求 TLS VirtualHost 自身含目标域名，且证书、key、SSLEngine 在同一个直接作用域。单/双引号 canonical 路径均覆盖；自定义路径、条件式证书和复杂配置在预检失败，不会探测或下载未知路径。

独立审查还发现 OpenSSL 配置命令可以在保留 canonical 证书指令的同时覆盖证书或私钥：Apache `SSLOpenSSLConfCmd Certificate/PrivateKey` 与 Nginx `ssl_conf_command Certificate/PrivateKey`。现在直接拒绝全部这两类命令（包括其他命令名和 Apache 大小写变体），不尝试枚举其效果或读取命令参数里的路径；动态 `ssl_*` 区块同样拒绝。

Apache 安全相关原始行还拒绝反斜杠语法：POSIX `shlex` 会消除 `exam\ple.com` 中的反斜杠，而 Apache 的 `ap_getword_conf` 不会按同样规则消除它。证书/key、include、ServerName/ServerAlias、SSL 指令和 VirtualHost 地址不能因此被归并为允许的 canonical 值。其他规则指令和 FilesMatch 等正则内容仍可含反斜杠，不是对整个主文件一律禁止。

标准 include 仅白名单识别，不递归下载、展开 glob 或调用 `GetDir`。Nginx 允许本站 well-known、extension、rewrite 和本站 PHP 分支 enable-php；Apache 允许本站 extension。其他 include 阻断预检。标准 include 的内容依然未知，不能排除额外证书或配置影响，因此默认配置的成功证据是：

| 证据字段 | 有标准 include | 无 include |
|---|---|---|
| `selected_site_main_configuration_verified` | `true` | `true` |
| `included_configuration_verified` | `false` | `true`（无待展开文件） |
| `selected_site_configuration_verified` | `false` | `true`（选定主文件证据） |
| `live_tls_verified` | `false` | `false` |
| `panel_sync_outcome_verified` | `false` | `false` |

成功文案明确为签发证书与主配置固定路径公开证书摘要一致，不宣称线上生效。无 include 的 `selected_site_configuration_verified` 仍不代表全局 Web 配置、进程 reload、网络 TLS 或其他同步位置已核验。

预检冻结主文件摘要；apply/deploy dispatch 比较摘要，申请/续签的只读恢复也拒绝无关配置漂移。独立 deploy 后允许预期的主文件变化，但必须重新通过相同 canonical 解析与公开证书核对。连续两次读回和摘要比较无法提供面板侧原子锁，读回后发生的并发修改仍可能存在。

已登记网站同步清单仍只描述 `GetSSL` 的 canonical 副本，并明确 incomplete；不会将未选择的 Node/Java 等项目主配置当成部署证据。否则其项目配置前缀差异会无关阻断所选 PHP 网站。清单仍不枚举孤立目录、未登记副本和面板 TLS。

## 保留的恢复与范围约束

保留固定 `baota_acme_panel_sync_v1`、`ssl_panel_sync` ACK、面板范围自动同步声明、独立部署意图、每次 dispatch 最多一个变更请求和断连不重发。canonical 新证书必须与已签发证书指纹一致且主文件确实指向 canonical，才可省略 `SetCertToSite`。续签订单 SAN 被裁剪或关联消失时保持待核实。TLS pin 变化不自动接受、不重发变更。

本次新读取不构造 `panelSite`、不使用会创建 rewrite 文件的 `GetFileBody`，缺失文件和根目录均保持缺失。既有 `GetSSL`、`get_orders` 等官方路由的初始化/证书库副作用仍按审计记录，不能把本次固定下载的边界扩大成整个 SSL 预检零写盘的承诺。
